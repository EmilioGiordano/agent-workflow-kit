### The loop
```
TASK -> implementer (own worktree) -> reviewer -> FAIL? -> same implementer fixes -> same reviewer re-reviews
                                              PASS -> merge <default-branch> -> gate -> push -> PR -> CI -> UI validation -> merge
```

### Who does what
| Action | Orchestrator | Implementer | Reviewer | User |
|---|---|---|---|---|
| Write TASKs, create branches and worktrees | yes | no | no | — |
| Commit on its branch | yes | yes | no | — |
| Push a branch, open a PR | yes | no | no | — |
| Merge a PR that meets the merge policy | <yes \| no> | no | no | <yes \| approves> |
| Push to `<default-branch>`, force-push, delete branches or worktrees | never | never | never | yes |

Anything not listed is not permitted by default.

### Branches and worktrees
- One branch per topic: `<type>/<topic>`, English. Types: `feat`, `fix`, `improve`, `refactor`, `perf`, `test`, `chore`, `build`, `docs`, `spike`.
- One branch, one worktree (at `worktree_root`), one implementer. Two branches that touch the same files never run in parallel.
- Each new worktree runs `worktree_setup` before the first commit.
- `TASK-*.md` and `REPORT*.md` are untracked (gitignored)<, and so is `.build-slot` (build lock only)>.

### Decisions taken on the way
Each branch records what it decided in `<decisions_log>` (tracked), in a commit on the branch:
```

```
`REPORT.md` is the orchestrator's untracked running report, not the decisions log.
